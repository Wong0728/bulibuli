# 已知问题与暂不支持清单

本文列出当前版本明确不提供的能力、已知的行为差异和尚未验证的范围，供选型和排障时对照。判定依据是仓库内的代码与门禁结果，不是运行验收结论；如果某项在后续版本落地，请同步删除本文对应条目。

## 链接解析支持的形态

解析入口在 `src/services/url_parser.rs`，只接受下列形式：

| 形态 | 说明 |
| --- | --- |
| `BV` 号 / `bilibili.com/video/BV...` | 普通视频，主用途 |
| `AV` 号 / `bilibili.com/video/av...` | 解析层支持，但使用面受限，见「AV 链接的提示与实际能力」 |
| `ep` 号 / `ss` 号 | 番剧单集与剧集季，返回分集列表 |
| `fp` 号 | 付费课程季，返回展平后的分集列表 |
| `b23.tv` 短链 | 最多跟随 3 跳重定向，最终地址必须落在 B 站 HTTPS 域白名单内，否则拒绝 |

不属于以上形态的输入会被拒绝，后端返回「不支持的B站链接，支持 BV/AV/ep/ss/fp/b23.tv」。

## 暂不支持的链接类型

以下 B 站页面形态不会被解析，粘贴进来只会得到上面的「不支持」错误，程序也不会下载它们：

- 收藏夹（`ml` 号）
- 稍后再看
- 观看历史
- 用户动态（含动态里的视频卡片整批导入）
- 音乐（`au` 号、`am` 号）
- 每周必看
- 互动视频（分支剧情类视频）
- 合集·链式：**只支持按 UP 主 UID 拉取合集列表，粘贴合集链接不会解析**

## 画质上限

取流与下载的画质代码白名单为 `16/32/64/74/80/112/116/120/125`（`/api/download/start` 与 `/api/video/get-video-urls` 同一口径）。

- **不提供 8K（127）与杜比视界（126）**：白名单外的值一律被拒绝并返回「不支持的视频画质代码」，程序不会静默降到 125。
- 下载抽屉的画质选项不含这两档；设置页的默认画质下拉仍然列出 126/127，并标注「仅在线观看可用，下载暂不支持」。这两档没有被下载白名单校验拦住写入设置，所以如果曾把默认画质存成 126 或 127，建议改回 125 及以下，否则取流与下载请求可能被拒。
- 默认画质为 1080P（80）。能否取到更高档位取决于账号权益与上游返回的流，程序不做超解。

## 网络与代理

- **没有出站代理**。设置和 `data/security.toml` 里的 `proxy` 是**入站访问模式**（服务只绑定 `127.0.0.1`，前面挂反向代理），与「让程序走代理去下载」无关。对 B 站的 HTTP 请求与内置 aria2c 的下载链路都没有代理配置项，aria2c 的启动参数中也不含代理选项。需要代理出口时，只能自行在部署环境层面处理。
- **没有按地理位置选择 CDN**。只做劣质节点识别：命中 MCDN/PCDN 域关键字的地址会记一条 WARN 并提示，连续失败的 host 会被临时拉黑一段时间，但这不等同于按地区挑最近节点，也不承诺选到最快线路。
- 默认只监听 `127.0.0.1`，开放局域网访问需要显式切换模式并重启。

## 更新清单的完整性

应用内更新读取 GitHub Release 中的 `latest.json` 获取版本与资产清单。清单有同名 SHA-256 文件 `latest.json.sha256`，但**没有独立签名**（无代码签名/清单签名体系），而且更新链路本身不会用这个文件验证清单——校验值和清单来自同一个 GitHub 通道，同通道取回的值不能自证。

现有缓解措施：

- 清单中的 `download_url` 受信任域白名单约束，只允许 `github.com`、`objects.githubusercontent.com`、`release-assets.githubusercontent.com`，且必须是 HTTPS。
- 每个归档都带同名 `.sha256` 资产，下载后先做 SHA-256 校验再解压替换；校验或替换失败时保留原版本继续运行。
- 发布工作流在上传前用 `sha256sum -c` 把 `latest.json.sha256` 和各归档的 `.sha256` 一起核对，防止发布环节内部的错配。
- 自动更新只替换程序文件，不触碰 `data/`。

残余威胁模型：SHA-256 只能证明下载内容与清单一致，不能证明清单本身可信。如果项目的 GitHub 账号或发布流水线被攻破，攻击者可以同时替换清单与资产，此时全部开启自动更新的设备会被静默换包。这属于发布通道可信性问题（代码签名/清单签名范畴），不是上述校验实现的缺陷。

建议：安全敏感或对来源有强要求的环境，把设置页的更新策略设为「关闭」，改为人工从 Release 页下载并核对 SHA-256 后升级。

## AV 链接的提示与实际能力

- 后端解析层已实现 `AV` 号（`url_parser.rs` 的 `AV_RE`），`/api/video/resolve` 会把 `av` 输入识别为 `video_av`。
- 但手动下载页拿到 `video_av` 后没有换取视频信息的分支，界面会落到空结果并提示「暂不支持 AV 链接，请使用 BV 链接（可在视频页地址栏复制）」（`web/src/views/TabManual.vue`）。
- 本机控制命令 `bulibuli ctl dl add` 同样只接受 BV，`AV/ep/ss/fp` 会明确返回「暂未支持」。

因此这条提示反映的是当前的实际可用范围，但措辞与解析能力不完全一致，属待修文案与待补前端路径。**现阶段请统一粘贴 BV 链接**，避免误以为解析失败。

- 强杀进程后的恢复（macOS/Termux 上的 aria2/FFmpeg 回收）与真实浏览器跨端口交接、局域网另一台设备访问、完整备份恢复、各平台密钥环，均未纳入自动化验证，静态代码检查不能替代这些运行验收。
