# 直播页面与录制链路审查报告（2026-08-10）

> 审查范围：直播页 DOM/CSS/JavaScript、直播 API、中间层状态同步、直播源与排期、B 站直播 API、弹幕 WebSocket、FFmpeg 录制/分段/合并、数据库持久化、故障恢复、可访问性与测试覆盖。
>
> 本文只列问题和整改方向，不包含代码修改。结论基于当前工作区源码、`data/logs` 中的实际运行日志、只读查询 `data/database/app.db` 的结果，以及 2026-08-10 执行的本地测试。

## 1. 结论摘要

当前直播模块不是单纯的“页面难看”，而是 **页面信息架构、状态模型、B 站协议适配和录制生命周期同时存在缺口**。最需要先处理的不是换颜色或调间距，而是下面四件事：

1. **弹幕新版接口缺少 WBI 签名，当前 `-352` 是可由源码直接解释的确定性问题。** 项目自己的 API 文档明确写着 `getDanmuInfo` 必须携带 `w_rid`/`wts`，但实际实现没有签名。
2. **旧版 `getConf` 回退没有真正恢复可用性。** 实际运行在多个房间上都进入“拿到旧配置但 WebSocket 认证回复失败”的循环；当前实现又会无限重连，持续制造请求和日志。
3. **前端把“后端 dashboard 请求成功”当成“B 站状态是新的”。** 风控全局退避时，页面仍会显示“刚刚已同步”，用户会被过期的开播/录制状态误导。
4. **录制状态机缺少自动恢复和可取消启动。** FFmpeg 在弹幕配置和数据库落盘之前就已经启动；启动期间不能停止；FFmpeg 意外退出后会一直占着会话，自动监控也不会重新拉起。

建议优先级：先修复 P0/P1 状态与协议问题，再重做页面布局。否则新 UI 只会更漂亮地展示错误状态。

### 严重度定义

| 级别 | 含义 |
|---|---|
| P0 | 当前核心能力已不可用、可能造成录制数据损坏/丢失，或会持续放大外部风控 |
| P1 | 高概率误导用户、导致漏录/重复录制/无法恢复，或造成明显的状态不一致 |
| P2 | 功能不完整、可观测性差、规模化后明显恶化，或重要 UX/无障碍问题 |
| P3 | 视觉、文案、一致性和易用性问题 |

## 2. 本次运行的真实故障链

### 2.1 已观察事实

- `data/logs/app.log.2026-08-10:372-398`：房间 `8178490` 的视频录制成功启动；新版 `getDanmuInfo` 返回 `-352`；旧版回退后 WebSocket 认证连续失败；视频最终仍被停止并合并。
- 同一日志的 `234-258`：房间 `1871977513` 也出现相同链路，不是单房间偶发现象。
- `data/logs/app.log.2026-08-09:667-693`：旧实现重连 3 次后把互动采集标记为不可用；当前源码已改为无限重连，但文件头注释仍写“最多 3 次”。
- 只读数据库查询显示最近 3 条 `live_recordings` 全部为 `stopped`；其中两条 `capture_mode=standard`、`interaction_status=degraded`、`danmaku_count=0`、`interaction_error=接收认证回复失败`。
- 说明“仅视频录制”的降级确实发生了，但页面没有用足够显眼、可操作的方式表达这一事实。

### 2.2 直接根因

`docs/bilibili-live-api.md:474-476` 明确记录：新版 `getDanmuInfo` 自 2025 年起需要 WBI 签名，并给出 `w_rid`、`wts` 参数。项目已经有完整的 `wbi::enc_wbi` 和 WBI key 缓存实现；但 `src/services/bili_api/live.rs:276-287` 只传入 `id`、`type`，没有签名。因此本次 `-352` 不是“B 站偶发抽风”，而是当前调用契约不完整。

同时，`src/services/bili_api/models/live.rs:3` 仍声称相关接口“不需要 WBI 签名”，与项目自己的文档和实际日志直接冲突。这会继续误导维护者。

## 10. 对照同类实现后的设计建议

本节不是要求照搬，而是用成熟项目验证“直播录制产品通常必须解决哪些问题”。

- [BililiveRecorder](https://github.com/BililiveRecorder/BililiveRecorder) 把“自动开播录制、多房间并行、破损直播流修复”列为核心能力，并特别说明直接由 FFmpeg 处理破损流可能使恢复更困难。当前项目的唯一主路径是 FFmpeg `-c copy`，却没有流修复、候选线路重试或可恢复 UI，应把“可靠保留原始数据”放在“一律立即转 MP4”之前。
- [BililiveRecorder-WebUI](https://github.com/BililiveRecorder/BililiveRecorder-WebUI) 将管理 WebUI 作为独立产品维护，采用 Vue3 + TypeScript + UI 组件库。可借鉴的不是技术栈本身，而是把房间状态、录制控制、配置和多实例健康视为明确的页面模型，而不是在一个 Tab 中拼接多个 `innerHTML` 模板。
- [biliup](https://github.com/biliup/biliup) 和其[文档](https://biliup.github.io/biliup/)明确把 Web 快速配置和录制状态查看作为完整工作流。当前页面只有“正在录什么”，没有“录完在哪里、失败怎么恢复、自动策略下一次何时生效”。
- `blrec` 的原仓库已经声明停止维护并迁移到其他项目，因此不建议把其旧接口细节当作当前 B 站协议依据；可以只参考其录制任务/历史/切片交互，而不能照抄旧 API。

建议的新页面骨架：

1. **顶栏健康摘要**：监控 worker、B 站检查新鲜度、直播中、录制中、互动降级、磁盘余量。
2. **房间主列表**：稳定排序；一张卡同时展示直播状态、自动策略、视频录制状态、互动状态、最后检查、下次计划。
3. **选中房间详情**：当前分段/质量/速度/文件大小、错误与重试、互动时间轴；不要让全局互动区脱离房间上下文。
4. **最近录制/待恢复**：播放或打开目录、查看互动归档、重试合并、保留/清理残片。
5. **添加/编辑抽屉**：支持直播 URL、房间号、批量导入；默认自动录制关闭；用结构化排期编辑器。
